# v1.2 详细设计方案：语义反射压缩 + 自适应压缩

## 背景

v1.1.0 的 3-block cache-stable architecture 解决了**缓存效率**问题（prefix cache hit rate >96%），
但压缩质量仍停留在启发式截断层面。`reflectiveBrief()` 本质上是正则匹配+硬截断，不理解语义。

v1.2 目标：在 3-block 架构之上叠加**语义理解层**，使压缩从"截断"进化为"理解后提炼"。

## 现有基础设施审计

### 已有能力（可直接复用）

| 模块 | 位置 | 能力 | v1.2复用 |
|------|------|------|---------|
| `embeddings.py` | MCP server | ONNX sentence-transformer，paraphrase-multilingual-MiniLM-L12-v2 | 用于语义相似度判断 |
| `memory_pressure_monitor.py` | MCP server | PressureLevel (NORMAL/L1/L2/L3)，RetentionType (FULL_RAW/SUMMARY_PLUS_KEY/SUMMARY_ONLY/NONE) | 用于自适应阈值 |
| `_log_tool_call()` | MCP server | JSONL日志，rotation at 1MB | 用于recall信号采集 |
| `InjectedBlockState` | Plugin | registryHash/warmHash 哈希比较 | 扩展为adaptive state |
| `topic_store.update()` | MCP server | 任意字段更新 + atomic write | 承载 reflectiveBrief 字段 |

### 当前压缩链路（逐层分析）

```
磁盘数据 → Plugin读取 → 格式化 → 注入system prompt
   │            │            │           │
   ▼            ▼            ▼           ▼
topic.json   resolveActive  reflective   3-block
summary=     Topic()        Brief()      format
"原始文本"    读磁盘        截断/正则     注入
```

**信息损失点：**
1. `reflectiveBrief()` — 从summary提取"At:/Progress:"前缀或第一句 → 非结构化内容直接截断
2. `truncate(scope, 80)` — scope硬截断到80字符 → 可能丢失关键限定词
3. `maxTopics=5` — 最多展示5个话题 → 第6个开始完全不可见
4. Warm Brief — 只取每个相关话题的一行摘要 → 无法展示关系语义

## 方案一：语义反射压缩（Semantic Reflective Compression）

### 核心思想

不改变注入时的压缩逻辑（保持3-block格式不变），而是**改变写入时的压缩质量**。

当前流程：
```
Agent工作 → 交互结束 → topic_update(summary="正在修复#168的dispatch bug...") → 磁盘存储原始文本
                                                                                    ↓
下一轮注入 → reflectiveBrief("正在修复#168的dispatch bug...") → 正则截断 → ~30 tokens
```

改进后：
```
Agent工作 → 交互结束 → topic_update(summary="原始文本") → 触发reflective summarization
                                                           ↓
                                                     MCP server调用LLM
                                                     生成reflective_brief
                                                     (≤30 tokens, 语义提炼)
                                                           ↓
                                                     磁盘存储两个字段:
                                                     summary="原始完整文本"
                                                     reflective_brief="语义提炼"
                                                           ↓
下一轮注入 → 直接读reflective_brief → 无需截断 → ~30 tokens 高质量摘要
```

**关键转变**：压缩从"注入时截断"移到"写入时提炼"。注入时直接用已压缩好的brief，零损失。

### 为什么这比LLMLingua/Prompt Compression更好

| 对比 | LLMLingua等 | 我们的方案 |
|------|-----------|---------|
| 压缩时机 | 每次注入前实时压缩 | 交互结束后异步压缩一次 |
| 计算成本 | 每轮都付 | 每次交互只付一次 |
| 压缩质量 | 通用NLP，不理解项目语境 | Agent自己写，理解项目语境 |
| 延迟 | 注入路径上增加延迟 | 写入路径，不影响注入 |
| 缓存友好 | 压缩结果每次可能不同 → 缓存失效 | brief固定 → 缓存友好 |

### 数据模型变更

**topic JSON 新增字段：**

```json
{
  "id": "fish-trail-v1.2",
  "title": "Fish Trail v1.2 Memory Research",
  "scope": "...",
  "summary": "完整的多行原始摘要，可以很长，包含所有历史细节...",
  "reflective_brief": "v1.2 design: semantic reflective compression + adaptive tier switching",
  "brief_generated_at": "2026-05-25T10:30:00Z",
  "brief_model": "deepseek-v4-flash",
  "tags": ["memory", "compression"],
  "status": "active"
}
```

**`reflective_brief` 生成规则：**
- ≤40 tokens（比当前的120字符limit更精确）
- 必须包含：当前阶段 + 核心动作/决策
- 格式自由，不强制"At:/Progress:"前缀
- 每次topic_update时异步重新生成

### 实现架构

```
┌─────────────────────────────────────────────────┐
│ Plugin (system-prompt-context-inject.ts)         │
│                                                  │
│ formatActiveFocusCompact():                      │
│   - 读 reflective_brief（优先）                   │
│   - fallback到 summary → reflectiveBrief()截断    │
│   - 无reflective_brief = 向后兼容                 │
└─────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────┐
│ MCP Server (server.py)                           │
│                                                  │
│ _handle_topic_update(args):                      │
│   1. 正常更新 topic 字段                          │
│   2. 如果 summary 变更：                          │
│      a. 检查 reflective_brief 是否过期            │
│      b. 触发异步 reflective compression           │
│   3. 返回更新后的 topic                           │
│                                                  │
│ _reflective_compress(summary, topic_id):         │
│   1. 调用配置的LLM endpoint                       │
│   2. prompt: "用≤40 tokens总结以下内容的最新状态"  │
│   3. 写入 reflective_brief + brief_generated_at   │
│   4. 失败 → 保留旧brief或fallback到启发式         │
└─────────────────────────────────────────────────┘
```

### LLM调用方案

**选项A：MCP server直接调用外部LLM API**
- 优点：完全异步，不占用主Agent的context
- 缺点：需要额外API key配置，增加依赖
- 成本：DeepSeek V4 Flash ~0.001元/次（每次30 tokens输出）

**选项B：通过OpenCode的client接口调用**
- 优点：复用已有的API配置
- 缺点：需要OpenCode暴露chat completion接口给plugin
- 可行性：当前不确定OpenCode plugin能否直接调用LLM

**选项C：Agent自己生成，写入MCP**
- 优点：零额外API成本，Agent理解上下文最好
- 缺点：依赖Agent行为规范（需要rules强制）
- 实现：在fish-trail rules中增加"交互后必须调用topic_update并提供brief"

**推荐方案：选项C（Agent-in-the-loop）为主 + MCP server端自动降级为fallback**

理由：
1. Agent写brief的质量最高（它理解当前交互的全部上下文）
2. 不增加外部依赖
3. MCP server端做强制校验和自动降级（见§"Brief质量控制"），不依赖Agent自觉
4. 无效brief → server自动用启发式截断替代
5. 未来可选加选项A作为离线优化

### Brief质量控制（Momus #1修复）

**三层防线：**

```
Layer 1: Schema校验（MCP server端，_handle_topic_update时执行）
  ├── maxLength: reflective_brief ≤200字符（≈40-80 tokens，覆盖中英文）
  ├── minLength: ≥10字符（拒绝"OK"、"完成"等无信息输入）
  ├── 拒绝低质量模式：/^(继续|ongoing|working on it|进行中)$/i
  ├── 拒绝纯标点/空白
  └── 校验失败 → 拒绝写入brief，返回warning

Layer 2: 自动降级（MCP server端，topic_update时执行）
  ├── 如果topic有summary但无reflective_brief
  │   └── 自动调用 _heuristic_brief(summary) 生成截断版brief
  │       └── 标记 brief_model="heuristic"，brief_generated_at=now
  ├── 如果brief超过7天未更新（brief_stale_days配置项，默认7）
  │   └── 标记为stale，Plugin端可选择忽略stale brief
  └── 如果Agent连续N次（默认3次）提交无效brief
      └── 降级到pure heuristic模式，不再期望Agent提供brief

Layer 3: 监控（Plugin端，注入时执行）
  ├── 统计brief使用率：有brief的topic占比
  ├── 统计brief质量：heuristic占比 vs agent-written占比
  └── 写入 _brief_metrics 到 injected-block-state.json
```

**Heuristic Fallback实现：**

```python
def _heuristic_brief(summary: str, max_chars: int = 200) -> str:
    """当Agent未提供brief时，用启发式方法从summary生成。"""
    if not summary:
        return ""
    # 复用Plugin端的reflectiveBrief逻辑，但作为server端fallback
    import re
    # Strategy 1: "At:/Progress:/Status:" prefix
    m = re.search(r'(?:At|Progress|Status)[:]\s*(.+?)(?:\.|$)', summary, re.M)
    if m and len(m.group(1).strip()) >= 10:
        brief = m.group(1).strip()
        return brief[:max_chars] + ("…" if len(brief) > max_chars else "")
    # Strategy 2: First sentence
    m = re.match(r'^(.+?[.!?])\s', summary)
    if m and len(m.group(1).strip()) >= 10:
        brief = m.group(1).strip()
        return brief[:max_chars] + ("…" if len(brief) > max_chars else "")
    # Strategy 3: Hard truncate
    return summary[:max_chars] + ("…" if len(summary) > max_chars else "")
```

**降级策略（自动检测Agent不配合）：**

```python
# topic JSON 新增字段
"brief_stats": {
    "agent_attempts": 5,     # Agent尝试提交brief的次数
    "agent_accepted": 3,     # 通过校验的次数
    "agent_rejected": 2,     # 被schema校验拒绝的次数
    "heuristic_count": 4,    # 启发式fallback生成次数
    "degraded": false         # true=已降级，不再期望Agent
}

# 降级触发条件：
# agent_rejected / agent_attempts > 0.5 且 agent_attempts >= 3
# → 设置 degraded=true，后续topic_update忽略reflective_brief参数
```

### 向后兼容

- 无 `reflective_brief` 字段 → fallback到现有 `reflectiveBrief()` 截断
- 旧版plugin读新topic JSON → 忽略未知字段，无影响
- 新版plugin读旧topic JSON → 自动降级到截断

### 验收标准

1. 新交互后，topic JSON包含 `reflective_brief` 字段
2. brief长度 ≤200字符（≈40-80 tokens，覆盖中英文混合）

7. Agent连续3次提交无效brief → 自动降级到heuristic模式
8. 自动化测试：构造5种brief（有效中文、有效英文、过短、过长、低质量模式），校验通过/拒绝行为符合预期
9. 自动化测试：无brief的旧topic → Plugin行为与v1.1 byte-identical

## 方案二：自适应压缩（Adaptive Compression by Model Tier）

### 核心思想

根据Agent的实际行为信号（MCP调用频率）自动调整压缩深度，不需要手动配置 `compressionLevel`。

```
         ┌──────────────────────────────────┐
         │  观察Agent行为                    │
         │  (topic_show调用频率)             │
         └──────────┬───────────────────────┘
                    │
                    ▼
         ┌──────────────────────────────────┐
         │  recall_signal = 最近N轮的        │
         │  topic_show调用次数               │
         └──────────┬───────────────────────┘
                    │
            ┌───────┴───────┐
            │               │
    recall_signal      recall_signal
      ≤ threshold        > threshold
            │               │
            ▼               ▼
    保持compact       升级到full
    (当前格式OK)      (注入信息不够)
```

### 信号采集

**数据源：`mcp-call-log.jsonl`**

```json
{"ts":"2026-05-25T10:30:00Z","tool":"topic_show","ok":true,"duration_ms":12.3,"args":{"topic_id":"fish-trail-v1.2"}}
```

**采集逻辑（在Plugin端）：**

```typescript
async function measureRecallSignal(fishTrailDir: string): Promise<AdaptiveSignal> {
  // 读取 mcp-call-log.jsonl 最后100行
  // 计算3个信号维度：
  //   1. topic_show_frequency: 最近20条记录中topic_show调用占比 (0.0~1.0)
  //   2. topic_show_recency: 最近一次topic_show距现在的记录数 (0~20)
  //   3. topic_show_failure_rate: topic_show调用中ok=false的占比 (0.0~1.0)
  // 返回综合信号对象
}
```

**为什么不在MCP server端做？**
- Plugin控制注入格式，决策必须在注入端
- MCP server只负责存储和查询
- Plugin已经读取fishTrailDir的其他文件（injected-block-state.json），再读一个log文件成本低

### 信号有效性验证（Momus #2修复）

**核心假设**：`topic_show` 调用频率与"Agent需要更多上下文"正相关。

**验证方法（实现前必须完成）：**

1. **历史数据分析**（P0前置任务）：
   - 分析已有 `mcp-call-log.jsonl`（如存在）
   - 统计 topic_show 调用与后续行为的关系：
     - topic_show 后是否跟着更多tool calls？（说明信息确实不够）
     - topic_show 后是否有用户纠正？（说明Agent判断失误）
     - topic_show 后是否有重复查询同一topic？（说明首次信息不足）
   - 如果没有历史数据：在v1.1.0-pre上收集最少50轮交互数据后再校准

2. **替代信号（多维度决策）**：

| 信号 | 含义 | 采集方式 | 权重 |
|------|------|---------|------|
| `topic_show_frequency` | 主动查询完整topic的频率 | mcp-call-log.jsonl | 0.4 |
| `topic_show_failure_rate` | topic_show调用失败率 | mcp-call-log.jsonl (ok=false) | 0.2 |
| `focus_block_size_delta` | Focus block注入前后token差变化 | Plugin端计算 | 0.2 |
| `user_correction_rate` | 用户纠正Agent的频率（"不对"/"我说的不是"） | future: 需要message分析 | 0.2 (future) |

3. **校准流程**：
   ```
   P0: 收集v1.1 baseline数据（50轮+）
      → 统计各信号分布
      → 确定初始阈值
   P1: 实现自适应，默认关闭（feature flag）
      → 开启后收集数据，对比baseline
   P2: 根据数据调整阈值和权重
      → 确认recall不降、token节省达标
   ```

4. **无效信号检测**：
   - 如果连续20轮信号为0（无任何topic_show调用）→ 标记为 `signal_cold`
   - cold状态下不自适应，保持compact
   - 如果信号振荡（compact→full→compact，每10轮一次）→ 标记为 `signal_unstable`
   - unstable状态下锁定为full（宁可多给信息）

### 自适应状态机

```
                    ┌─────────┐
                    │ UNKNOWN │ (初始状态)
                    └────┬────┘
                         │ 首次信号
                    ┌────┴────┐
                    │         │
            signal ≤ 0.1  signal > 0.3
                    │         │
                    ▼         ▼
              ┌─────────┐ ┌─────────┐
              │ COMPACT │ │  FULL   │
              └────┬────┘ └────┬────┘
                   │            │
           signal > 0.3    signal ≤ 0.1
           持续3轮          持续3轮
                   │            │
                   └─────┬──────┘
                         │ 切换
                         ▼
                    新状态持久化到
              injected-block-state.json
```

**迟滞设计**：不在单次信号变化时立即切换，而是要求信号**持续3轮**才切换。避免振荡。

**冷却期**：状态切换后，最少等待10轮才允许再次切换。防止边缘信号导致频繁切换。

**状态机增强：**

```
                    ┌─────────┐
                    │ UNKNOWN │ (初始状态，默认compact)
                    └────┬────┘
                         │ 首次信号
                    ┌────┴────┐
                    │         │
            signal ≤ 0.1  signal > 0.3
                    │         │
                    ▼         ▼
              ┌─────────┐ ┌─────────┐
              │ COMPACT │ │  FULL   │
              └────┬────┘ └────┬────┘
                   │            │
           signal > 0.3    signal ≤ 0.1
           持续3轮          持续3轮
           且冷却期已过      且冷却期已过
                   │            │
                   └─────┬──────┘
                         │ 切换
                         ▼
                   冷却期=10轮
                   持久化到磁盘
```

**信号振荡检测**：
- 记录最近5次状态切换的时间戳
- 如果5次切换发生在<50轮内 → 标记 `signal_unstable`
- unstable → 锁定为FULL（宁可多给信息），直到连续20轮信号稳定后解锁

### 与现有 compressionLevel 的关系

自适应模式与手动配置共存：

```typescript
// resolvePluginOptions 增加 adaptiveCompression 选项
interface PluginOptions {
  // ...
  compressionLevel?: "compact" | "full" | "adaptive"  // 新增 "adaptive"
  adaptiveCompression?: boolean  // legacy alias → maps to "adaptive"
}
```

| compressionLevel | 行为 |
|-----------------|------|
| `"compact"` | 强制compact，不自适应 |
| `"full"` | 强制full，不自适应 |
| `"adaptive"` | 默认值，根据信号自动切换 |

### 实现步骤

1. **Plugin: `measureRecallSignal()`** — 读取mcp-call-log.jsonl，计算最近N轮的topic_show频率
2. **Plugin: `resolveAdaptiveMode()`** — 状态机逻辑，读取/写入adaptiveState
3. **Plugin: `formatActiveFocusBlock()`** — 分支时读取自适应状态而非仅pluginOpts
4. **PluginOptions**: `compressionLevel` 新增 `"adaptive"` 选项，默认值改为 `"adaptive"`

### 成本分析

| 操作 | 频率 | 延迟 | 成本 |
|------|------|------|------|
| 读取mcp-call-log.jsonl | 每轮 | <1ms | 零（本地文件） |
| 状态机决策 | 每轮 | <0.1ms | 零 |
| 写入adaptiveState | 仅状态变更时 | <1ms | 零 |
| **总计额外开销** | — | **<2ms/轮** | **零API成本** |

### 验收标准

1. `compressionLevel="adaptive"` 模式下，初始为compact
2. Agent连续3轮触发topic_show（signal>0.3）且冷却期已过 → 自动切换到full
3. 切换后连续3轮无topic_show（signal<0.1）且冷却期已过 → 自动回退compact
4. `compressionLevel="compact"` 或 `"full"` → 行为与v1.1完全一致（不受自适应影响）
5. adaptiveState持久化到磁盘，重启后恢复
6. 冷却期：状态切换后10轮内不允许再次切换
7. 振荡检测：50轮内5次切换 → 锁定为full直到连续20轮稳定
8. mcp-call-log.jsonl不存在或为空 → 默认compact，静默（与v1.1一致）
9. 自动化测试：模拟20轮log数据，验证状态机按预期切换
10. 自动化测试：模拟振荡log数据，验证锁定行为

## 两个方案的集成点

```
方案一（语义反射压缩）     方案二（自适应压缩）
        │                          │
        │  改变brief写入质量        │  改变注入格式选择
        ▼                          ▼
   reflective_brief          adaptive state machine
   (topic JSON字段)          (injected-block-state.json)
        │                          │
        └──────────┬───────────────┘
                   │
                   ▼
          Plugin注入时：
          1. 读adaptive state → 决定compact/full
          2. 读reflective_brief（优先）或summary截断
          3. 组合格式化 → 注入
```

**两个方案完全解耦，可独立实现和发布：**
- 方案一改的是**数据质量**（brief怎么写）
- 方案二改的是**格式选择**（用compact还是full）
- 集成后效果叠加：compact模式下brief质量更高 + full模式自动切换保底

## 可观测性与发布策略（Momus #3修复）

### Feature Flags

两个方案各有一个feature flag，默认关闭：

**PluginOptions 扩展：**

```typescript
interface PluginOptions {
  // ...existing...
  compressionLevel?: "compact" | "full" | "adaptive"
  debug?: boolean
  // v1.2 feature flags
  reflectiveBriefEnabled?: boolean   // 方案一：默认 false
  adaptiveCompressionEnabled?: boolean // 方案二：默认 false (compressionLevel="adaptive"时自动true)
}
```

**opencode.json 示例：**

```json
{
  "plugin": [
    ["packs/core/fish-trail/.opencode/plugin/system-prompt-context-inject.ts", {
      "reflectiveBriefEnabled": true,
      "compressionLevel": "adaptive"
    }]
  ]
}
```

**降级行为：**
- `reflectiveBriefEnabled=false`（默认）→ Plugin完全忽略reflective_brief字段，行为与v1.1一致
- `compressionLevel="compact"` 或 `"full"` → 自适应逻辑完全跳过，与v1.1一致

### Metrics定义

**写入 `injected-block-state.json` 的 `_metrics` 字段：**

```json
{
  "_metrics": {
    "brief": {
      "total_topics": 8,
      "topics_with_brief": 6,
      "brief_hit_rate": 0.75,
      "heuristic_ratio": 0.33,
      "agent_reject_rate": 0.05,
      "avg_brief_chars": 87,
      "stale_briefs": 1
    },
    "adaptive": {
      "current_mode": "compact",
      "mode_switches_total": 3,
      "avg_signal": 0.12,
      "signal_p95": 0.45,
      "unstable_locks": 0,
      "cold_starts": 1,
      "last_switch_rounds_ago": 15
    },
    "performance": {
      "signal_measurement_ms_avg": 0.8,
      "signal_measurement_ms_p99": 1.2,
      "state_write_ms_avg": 0.3
    }
  }
}
```

**Metrics更新频率**：每10轮更新一次（避免频繁写磁盘）。

**告警规则（供未来监控用）：**

| Metric | 阈值 | 告警 |
|--------|------|------|
| `agent_reject_rate > 0.5` | Agent过半brief被拒 | 提示检查rules是否生效 |
| `heuristic_ratio > 0.8` | 大部分brief是截断 | 提示Agent未配合 |
| `mode_switches_total > 10` in 100 rounds | 频繁切换 | 标记unstable |
| `signal_measurement_ms_p99 > 10` | 信号采集过慢 | 检查log文件大小 |

### 分阶段发布

```
Phase 0: 内部验证（当前）
  ├── feature flag默认关闭
  ├── 开发者手动开启测试
  └── 收集baseline metrics

Phase 1: 内部Alpha（1-2周）
  ├── reflectiveBriefEnabled=true
  ├── compressionLevel="compact"（自适应仍关闭）
  ├── 收集brief质量数据
  └── 校准信号阈值

Phase 2: 自适应Beta（1-2周）
  ├── compressionLevel="adaptive"
  ├── 监控metrics，验证状态机行为
  └── 调整阈值

Phase 3: 默认开启（稳定后）
  ├── reflectiveBriefEnabled=true（默认）
  ├── compressionLevel="adaptive"（默认）
  └── 保留手动override选项

Phase 4: 正式发布（v1.2.0 stable）
  ├── 移除feature flag（行为成为默认）
  └── 保留compressionLevel="compact"/"full"手动override
```

### 回滚方案

| 场景 | 回滚动作 |
|------|---------|
| brief质量差导致recall下降 | `reflectiveBriefEnabled=false` → 回退到v1.1截断 |
| 自适应频繁切换导致不稳定 | `compressionLevel="compact"` → 固定compact模式 |
| 两个方案都有问题 | 关闭两个flag → 完全回退到v1.1行为 |
| injected-block-state.json损坏 | 删除文件 → Plugin自动重建（cold start，与v1.1首次运行一致） |
| topic JSON reflective_brief字段异常 | Plugin忽略无法解析的brief → fallback到summary截断 |

## 风险与缓解

| 风险 | 影响 | 缓解 | 检测 |
|------|------|------|------|
| Agent不遵守brief格式rules | brief质量不一致 | Schema校验(3层防线) + 自动降级 | `agent_reject_rate` metric |
| Agent完全不提供brief | 方案一失效 | MCP server自动用heuristic fallback | `heuristic_ratio` metric |
| 自适应阈值不准 | 频繁切换或永不切换 | 迟滞(3轮)+冷却(10轮)+振荡锁定 | `mode_switches_total` metric |
| mcp-call-log.jsonl不存在 | 无信号 | 默认compact，与v1.1一致 | `cold_starts` metric |
| brief生成增加Agent认知负担 | Agent分心 | brief是自然副产物，schema校验防过度投入 | — |
| topic JSON字段膨胀 | 磁盘增长 | brief≤200字符，stats可忽略 | 磁盘监控 |
| injected-block-state.json损坏 | 状态丢失 | 删除重建（cold start安全） | 文件存在性检查 |
| 信号采集性能退化 | 注入延迟增加 | log文件rotation at 1MB，尾部读取 | `signal_measurement_ms_p99` metric |
| 多Agent共享topic时状态冲突 | brief互相覆盖 | atomic write + last-write-wins | — |
| 中文brief token计算不准 | 长度限制失效 | 用字符数(≤200)而非token数 | `avg_brief_chars` metric |
