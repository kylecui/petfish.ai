# v1.2 Post-Alpha L5 Upgrade Plan

> 基于Ch05《能力与契约层》分析 + 96个skill审计数据的升级规划

## 审计发现（Evidence Base）

### 1. Description质量（Tool Contract要素1）

| 指标 | 值 | 判定 |
|------|-----|------|
| 有排除条件（"什么时候不该用"） | 15/96 (16%) | **严重不足** |
| 有前置条件（"用我之前要满足什么"） | 17/96 (18%) | **严重不足** |
| 双语触发词覆盖（zh+en） | 73/96 (76%) | 可接受，但剩余23个纯英文 |

Ch05的核心结论：description是7要素中**对模型行为影响最大的字段**。好的description回答三个问题：什么时候用？前置条件是什么？什么情况不该用？

**现状**：84%的skill description只回答了第一个问题（"什么时候用"），完全没有排除条件和前置条件。这是trigger误匹配、skill之间混淆的根本原因。

### 2. Schema覆盖（Tool Contract要素2/3）

| 指标 | 值 | 判定 |
|------|-----|------|
| 有JSON Schema的skill | 7/96（research pack级，非skill级） | **几乎为零** |
| 有output schema的 | 0 | **完全缺失** |
| Schema与SKILL.md对齐 | 有已知历史问题（#82/#83/#78） | 已修复但无机制防回归 |

### 3. Skill分类（三层抽象）

Research pack 54个skill的分类：
- **Real Skill**（多步编排+内部流程）: 1个（research-router）
- **Adapter/Thin Skill**（领域增强+轻量检查清单）: 53个

这意味着53/54的"skill"在Ch05的框架下**不是Skill而是Tool或轻量Adapter**。它们不包含多步编排、状态管理、错误处理或原子性保障。这不是问题——adapter设计是我们有意为之的——但需要明确这个分类。

### 4. 能力发现（Capability Discovery）

当前的trigger机制本质是**静态注册**——agent在运行时通过description匹配来发现skill。这与Ch05 §5.7.1描述的静态模式一致，继承了其核心缺陷：每次修改skill description都需要人工验证trigger是否仍然准确。

## 升级目标

不照搬Ch05的企业级Tool Contract 7要素。根据PEtFiSh的场景（个人开发者AI助手，无高危副作用），聚焦**影响最大、成本最低**的3个改进：

1. **Description三问模型** — 直接提升trigger准确率
2. **Skill分类标签** — 帮助agent理解能力层级，减少路由混淆
3. **轻量Schema防护** — 防止schema/skill.md漂移回归

## 升级计划

### Phase A: Description升级（高优先级，高ROI）

**目标**：将所有96个skill description升级为"三问模型"格式

**规范**：

```yaml
# 好的description模板（三问模型）
description: |
  [做什么 + 什么时候用]. Use when [触发词列表].
  [前置条件]. Requires [前置条件].
  [排除条件]. Do NOT use for [排除场景], use [替代skill] instead.
```

**示例 — Before/After**：

Before（现状）:
```
Use this skill when the user wants to create, revise, expand, compress, 
or review actual course chapter content.
```

After（三问模型）:
```
Create, revise, expand, compress, or review course chapter content — 
explanations, examples, transitions, key takeaways, and teaching flow.
Use when user asks to write/rewrite/improve course content or chapter text.
Requires an existing outline (use course-outline-design first if none).
Do NOT use for outline design, lab steps, or QA review — use 
course-outline-design, course-lab-design, or course-quality-assurance instead.
```

**执行计划**：

| 步骤 | 内容 | 工作量 |
|------|------|--------|
| A1 | 建立description模板 + lint规则 | 1天 |
| A2 | 升级research pack 54个skill description | 2天（批量） |
| A3 | 升级其余pack的42个skill description | 1天（批量） |
| A4 | 运行trigger eval验证改善 | 0.5天 |
| A5 | 更新skill-lint规则：检测三问覆盖率 | 0.5天 |

**验收标准**：
- 三问覆盖率：从16%提升至≥80%
- trigger eval准确率：baseline → +10%目标
- lint规则新增：`description-coverage` 检查

### Phase B: Skill分类标签（中优先级，中ROI）

**目标**：在SKILL.md frontmatter中新增 `category` 字段，明确skill的三层抽象分类

**新增字段**：

```yaml
---
name: research-router
category: router          # router | orchestrator | adapter | atomic
domain: research          # 所属Capability域
---
```

| category | 含义 | 示例 |
|----------|------|------|
| `router` | 能力路由器，分发到具体skill | research-router |
| `orchestrator` | 多步编排，内部管理状态 | course-development-orchestrator |
| `adapter` | 领域增强，补充检查清单 | travel-adapter, conference-adapter |
| `atomic` | 单一职责，无内部编排 | skill-lint, petfish-style-rewriter |

**执行计划**：

| 步骤 | 内容 | 工作量 |
|------|------|--------|
| B1 | 定义category规范 + 更新lint_skill.py | 1天 |
| B2 | 为96个skill标注category + domain | 1天 |
| B3 | companion gateway利用category优化路由 | 1天 |

**收益**：
- Agent可以区分"应该先问router"还是"直接调atomic skill"
- 减少大包（research 54个）的路由混淆
- 为未来的渐进式披露（Progressive Disclosure）打基础

### Phase C: Schema防护（低优先级，防回归）

**目标**：建立schema与SKILL.md的自动对齐检查，防止#82/#83/#78类问题回归

**方案**：在skill-lint中新增规则 `schema-field-alignment`

```
检查逻辑：
1. 读取 schemas/*.json 中定义的字段名
2. 读取 SKILL.md body 中引用的字段名
3. 计算交集/差集
4. 如果schema中有字段在SKILL.md中未提及 → WARN
5. 如果SKILL.md中引用字段在schema中不存在 → ERROR
```

**执行计划**：

| 步骤 | 内容 | 工作量 |
|------|------|--------|
| C1 | 实现schema-field-alignment lint规则 | 1天 |
| C2 | 在quality-gate中启用此规则 | 0.5天 |

**暂不做的要素**（企业级，当前不适用）：

| 要素 | 原因 |
|------|------|
| 要素4 permissions | PEtFiSh无用户角色体系 |
| 要素5 sideEffects | skill无高危副作用（不删库不重启服务） |
| 要素6 errorSemantics | skill失败代价低，无Saga补偿需求 |
| 要素7 executionBoundary | 无资源约束需求 |
| outputSchema标准化 | 当前skill输出是自然语言Markdown，结构化输出需更大架构变更 |

## 时间线

```
v1.2 Alpha → 测试团队体验（进行中）
    ↓ 收集反馈
Phase A (Description升级)     — 5天 — v1.3
Phase B (Skill分类标签)       — 3天 — v1.3
Phase C (Schema防护)          — 1.5天 — v1.3
    ↓
v1.3 Release — trigger准确率提升 + skill分类清晰化
```

Phase A和B可以并行。Phase C可以在A/B完成后补上。

## 不做的事（明确排除）

1. **不引入完整Tool Contract 7要素** — 我们的场景不需要permissions/sideEffects/errorSemantics/executionBoundary
2. **不重构skill内部编排为正式Saga模式** — adapter skill设计是有意为之的轻量化选择
3. **不引入动态能力发现** — 当前静态注册+marketplace-connector已满足需求
4. **不标准化outputSchema** — 投入产出比太低，当前自然语言输出对下游消费足够

## 风险

| 风险 | 缓解 |
|------|------|
| description加长导致token消耗增加 | 三问模型新增内容≈50-80 chars/skill，96个skill总增≈5-8KB，可控 |
| 批量修改description可能引入新错误 | 每次修改后跑trigger eval，自动验证 |
| category字段需要agent侧配合消费 | Phase B先标注，companion gateway逐步利用 |
