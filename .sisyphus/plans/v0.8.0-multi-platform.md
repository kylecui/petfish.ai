# v0.8.0 — Multi-Platform Instruction Generation

## Goal

Ship #63: when PEtFiSh installs packs, detect ALL AI platforms present in the target project and generate instruction files for each — not just the primary platform. Add content condensation for token-limited platforms, Claude Code Hooks for fish-trail enforcement, and codify the uv-first Python policy.

## Success Criteria

1. `--detect` returns ALL matching platforms (not first-match-wins)
2. Installer generates instruction files for every detected platform in a single run
3. Translation runs ONCE after all packs are merged (not N times inside the pack loop)
4. Platforms with token limits get condensed instruction files (deterministic, no LLM)
5. Claude Code platform gets `.claude/hooks/` scripts for fish-trail gateway enforcement
6. All Python-dependent scripts and MCP servers use uv; policy documented in AGENTS.md and README

## Non-Goals

- Converting inline `python3 -c` stdlib-only JSON parsing in installers to uv (no deps = no venv needed)
- LLM-based summarization for condensation
- Changing the primary platform install flow (skills dir, config merge, pack registry)
- Adding new platforms to platforms.json (only adding condensation config to existing ones)

## Phase 1: Multi-Detect and Post-Loop Translation

### 1.1 Change detect_platform to return ALL matches

**Files**: `remote-install.sh`, `install.sh`, `remote-install.ps1`, `install.ps1`

Current behavior: `detect_platform()` iterates platforms.json `detect_markers` and returns the FIRST match. The caller uses this single platform for the entire install.

New behavior:
- Rename `detect_platform()` → `detect_all_platforms()` (internal, returns newline-separated list of all matching platform keys)
- Keep `detect_platform()` as a wrapper that returns the first result (backward compat for `--platform` flag)
- When `--detect` is passed WITHOUT `--platform`, use the full list:
  - First platform in the list = primary (install skills, config, registry as today)
  - Remaining platforms = secondary (generate instruction files only)

**PowerShell equivalent**: `Get-DetectedPlatform` → `Get-AllDetectedPlatforms` (returns array), keep `Get-DetectedPlatform` as `[0]` wrapper.

**Detection order**: Follow `platform_groups.all` order from platforms.json: opencode, claude, codex, cursor, copilot, windsurf, antigravity. First match in this order = primary.

**Edge cases**:
- `--platform X` explicitly set → use X as primary, still detect others for instruction translation
- `--platform all` → install skills to ALL platforms (existing behavior, no change)
- No markers found → fall back to `universal` (existing behavior)
- `opencode` always matches if `.opencode/` exists (which it does after install) — do NOT auto-detect opencode as secondary since AGENTS.md is already the primary file

### 1.2 Move translation to post-install step

**Files**: `remote-install.sh`, `install.sh`, `remote-install.ps1`, `install.ps1`

Current behavior (remote-install.sh lines 902-906): `update_translated_instructions` runs inside the per-pack install loop, after each pack's AGENTS.md merge. This means it runs N times (once per pack), each time reading the cumulative AGENTS.md and overwriting the same target file. The last run wins, making runs 1..N-1 wasted.

New behavior:
- Remove `update_translated_instructions` call from inside the pack loop
- Add a new post-loop step `generate_secondary_instructions()` that:
  1. Reads the final merged AGENTS.md once
  2. For each detected secondary platform that has `instructions_translation` in platforms.json:
     - Apply the translation method (rename_with_header, wrap_as_mdc, marker_based)
     - Apply condensation if the platform has a `condense` config (Phase 2)
     - Write the target file
  3. For antigravity: handle the existing special-case GEMINI.md generation
- This function runs exactly ONCE after all packs are installed

**Validation**: After install, verify each expected instruction file exists and is non-empty.

### 1.3 Update platforms.json

No structural changes in Phase 1. The `instructions_translation` config already contains all needed info (source, target, method). Phase 2 adds `condense` config.

- [ ] `generate_secondary_instructions()` / `New-SecondaryInstructions` post-loop step in all 4 installers

## Phase 2: Content Condensation

### 2.1 Condensation strategy

Problem: Some platforms have strict token/line limits on instruction files:
- Windsurf: ~6,000 tokens effective context
- Cursor .mdc: ~500 lines practical limit
- Claude Code CLAUDE.md: ~200 lines recommended (though no hard limit)

Strategy: **Deterministic priority-based section extraction** (no LLM).

Algorithm:
1. Parse AGENTS.md into sections (split on `<!-- BEGIN pack: ... -->` / `<!-- END pack: ... -->` markers)
2. Classify each section by priority:
   - **P0 (always include)**: Companion Gateway (topic check + skill sense + debug mode), fish-trail always-on behavior, `/petfish` commands table
   - **P1 (include if space)**: Pack-specific AGENTS.md rules (deploy, course, calibrate, etc.)
   - **P2 (drop first)**: Verbose examples, extended tables, detailed sub-rules
3. Estimate token count: `len(text) / 4` (chars-to-tokens heuristic, conservative for mixed CJK/ASCII)
4. If total tokens ≤ platform limit → use full content
5. If over limit → include P0, then add P1 sections until budget exhausted, drop P2
6. If still over after dropping P2 → truncate P1 sections to their first paragraph + heading only
7. Append a footer: `<!-- Condensed by PEtFiSh. Full rules: AGENTS.md -->`

### 2.2 platforms.json changes

Add `condense` config to platforms that need it:

```json
"windsurf": {
  ...
  "condense": {
    "max_tokens": 6000,
    "priority_sections": ["companion-gateway", "fish-trail", "petfish-commands"]
  }
},
"cursor": {
  ...
  "condense": {
    "max_tokens": 8000,
    "priority_sections": ["companion-gateway", "fish-trail", "petfish-commands"]
  }
}
```

Platforms WITHOUT `condense` (claude, copilot, codex) get full content.

### 2.3 Implementation location

Condensation logic lives in the installer scripts themselves (bash function `condense_content()` / PowerShell `Compress-InstructionContent`). It uses only shell string operations + the `python3 -c` pattern already used for JSON parsing (stdlib only, no uv needed).

Alternative considered: External Python script. Rejected — adds a dependency step and the logic is simple enough for shell + inline python.

- [ ] `condense` config added to windsurf and cursor in platforms.json
- [ ] `condense_content()` / `Compress-InstructionContent` function in all 4 installers
- [ ] Integration into `generate_secondary_instructions()` from Phase 1

## Phase 3: Claude Code Hooks

### 3.1 Hook scripts

Create 3 shell scripts in `packs/core/fish-trail/.claude/hooks/`:

**fish-trail-gateway.sh** (UserPromptSubmit hook):
- Checks if fish-trail MCP is running (quick TCP or process check)
- If running: outputs a one-line reminder for the LLM: "🐟 fish-trail active. Run topic_detect before processing."
- If not running: outputs nothing (silent degradation, matching existing AGENTS.md behavior)
- stdout becomes `additionalContext` in Claude Code

**fish-trail-precompact.sh** (PreCompact hook):
- Outputs current topic summary and active topic ID as context to preserve through compaction
- Reads topic registry from `.petfish/fish-trail/topic-registry.json` and active topic data from `.petfish/fish-trail/topics/<id>.json` (paths per `topic_store.py:31-37`)
- If `.petfish/fish-trail/` missing or no active topic: outputs nothing

**fish-trail-postcompact.sh** (PostCompact hook):
- Re-injects fish-trail awareness after compaction
- Outputs: "🐟 Session compacted. fish-trail topic governance is active. Call topic_detect on next user message."

All scripts: `#!/usr/bin/env bash`, exit 0 always (hooks must not block), timeout-safe (< 2s).

### 3.2 Settings merge

The installer already has config merge logic for `opencode.json`. Extend it to merge `.claude/settings.json` when platform is claude.

Hook config to merge into `.claude/settings.json`:

```json
{
  "hooks": {
    "UserPromptSubmit": [{
      "hooks": [{
        "type": "command",
        "command": "bash .claude/hooks/fish-trail-gateway.sh",
        "timeout": 5
      }]
    }],
    "PreCompact": [{
      "hooks": [{
        "type": "command",
        "command": "bash .claude/hooks/fish-trail-precompact.sh",
        "timeout": 5
      }]
    }],
    "PostCompact": [{
      "hooks": [{
        "type": "command",
        "command": "bash .claude/hooks/fish-trail-postcompact.sh",
        "timeout": 5
      }]
    }]
  }
}
```

Merge strategy: if `.claude/settings.json` exists, deep-merge the `hooks` key (preserve existing hooks, append ours). If not, create the file.

## Phase 4: uv-First Python Policy

### 4.1 Scope

Codify the existing practice: all PEtFiSh Python scripts that have external dependencies MUST use uv for environment management. This is documentation + normalization, not a rewrite.

### 4.2 What to normalize

1. **MCP server configs**: Verify all `opencode.example.json` files use `["uv", "run", ...]` (most already do)
2. **Script shebangs**: Scripts with `#!/usr/bin/env python3` that import non-stdlib packages → change to `#!/usr/bin/env -S uv run` with PEP 723 inline metadata (or ensure pyproject.toml exists in the pack)
3. **Installer uv check**: Already warns when uv is missing. No change needed.

### 4.3 What NOT to touch

- Inline `python3 -c` in installer scripts (stdlib-only, no deps)
- Scripts that only use stdlib (no reason to add uv overhead)
- Existing scripts that already have uv shebangs (already compliant)

### 4.4 Documentation

Add a "Python Environment Policy" section to:
- **AGENTS.md**: Under a new top-level section, 5-8 lines stating the policy
- **README.md**: In Prerequisites section, expand the uv mention

Content:
- All PEtFiSh Python scripts with external dependencies use uv
- MCP servers launched via `uv run`
- Standalone scripts use PEP 723 inline metadata OR pack-level pyproject.toml
- `pip install` is not used anywhere in PEtFiSh
- Installers warn if uv is not found
