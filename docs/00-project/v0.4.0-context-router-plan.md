# v0.4.0 开发计划：Context Router — 话题治理器

## 版本目标

为PEtFiSh增加上下文治理能力。目标不是生成对话摘要，而是在项目内维护topic边界、继承策略和切换记录，降低跨话题上下文污染。

核心问题：当用户切换话题时，系统需要判断当前上下文应完全继承、部分继承，还是直接隔离。判断依据是topic间的关系类型和污染风险评分。

## 范围

**包含：**

- Topic生命周期管理（创建、更新、归档、搜索、关系图）
- 话题变更检测与关系分类（7种类型）
- 污染风险评分（5维度规则引擎）
- Context Package生成（继承包、桥接包、导出包）
- 决策日志（每次路由决策可追溯）
- AGENTS.md always-on规则（安装时注入目标项目）
- MCP server（stdio transport，纯Python，零外部依赖）

**不包含：**

- 跨项目topic共享（每个项目独立`.ai-context/`）
- 数据库后端（JSON文件足够）
- ML/LLM驱动的topic检测（纯规则+关键词）
- Web UI或可视化界面
- `/petfish topics`子命令（延迟到v0.5.0验证核心循环后再加）

## 验收标准

1. 18个MCP tools全部可通过stdio调用，返回结构化JSON
2. `topic_detect`对evals中20条正负样本的分类准确率≥80%
3. 污染评分在3组预设场景下的输出与预期等级一致
4. AGENTS.md注入后，MCP不可用时graceful降级（无报错，退化为手动模式）
5. 全部pytest测试通过，CI绿灯
6. `install.ps1 -Pack context`和`install.sh --pack context`均可正常安装

## 产出物

### 1. context-router skill pack

包含skill + MCP server，alias为`context`。

### 2. 三层架构

- **Layer 1 (AGENTS.md)**：安装时合并到目标项目指令文件。每次交互前通过MCP调用`topic_detect`检查topic状态，根据风险等级决定静默、提示或触发深度治理。当MCP不可用时（server未启动、连接失败），退化为无感知模式——不报错，不阻塞正常工作，在回复中附带一行提示"context-router MCP未连接，话题治理未激活"。
- **Layer 2 (MCP: context-state)**：Python MCP server，stdio transport。持久化topic registry、context package、decision log到项目级`.ai-context/`目录。暴露18个tools。状态文件格式为JSON。
- **Layer 3 (SKILL.md)**：深度治理方法论。5步工作流，7种关系类型，污染风险评分，Context Package模板。风险≥high或用户主动触发时加载。

### 5. 本地存储结构

安装后在目标项目中创建：

```
.ai-context/
├── topic-registry.json
├── topics/
│   └── <topic-id>.json
├── contexts/
│   └── <topic-id>.context.md
└── decisions/
    └── decision-log.json
```

所有结构化数据使用JSON格式（Python stdlib原生支持，零外部依赖）。Context Package本身为Markdown（人可读，适合作为agent上下文输入）。

### 6. Topic关系模型

7种关系类型：

| 关系 | 含义 | 上下文策略 | 检测信号 |
|------|------|-----------|---------|
| continue | 继续当前话题 | 完全继承 | 语义延续、同一领域关键词 |
| fork | 从当前话题分叉 | 继承部分上下文，创建子topic | "另外"、"顺便"、子任务拆分 |
| switch | 切换到已有话题 | 加载目标topic的Context Package | 引用已知topic名称/ID |
| merge | 合并两个话题 | 生成合并摘要，标记来源 | "把X和Y合到一起"、交叉引用 |
| archive | 归档完成话题 | 冻结上下文，只保留摘要 | "这个做完了"、显式关闭 |
| reset | 明确清空上下文 | 建立干净上下文包 | "重新开始"、"忘掉前面的" |
| bridge | 两个话题间建立桥接 | 只继承交叉部分 | 两个topic共享部分概念但目标不同 |

检测可靠性说明：continue、switch、fork、reset四种类型可通过规则+关键词高可靠检测。merge、archive、bridge三种依赖更多上下文信号，检测置信度较低时应提示用户确认而非自动执行。

### 7. 污染风险评分

5个维度，每维度0-20分，总分0-100：

```
污染风险 = 话题距离 + 目标冲突 + 术语重载 + 输出格式差异 + 历史偏置强度
```

**权重设计理由**：初版采用等权（每维度20分）是因为缺乏真实使用数据来确定差异权重。每个维度的评分范围相同，便于用户理解和手动调整。后续版本可根据decision log中的用户覆盖率（用户推翻系统建议的频率）来调整各维度权重。

**各维度定义**：

| 维度 | 评分依据 | 0分（无风险） | 20分（高风险） |
|------|---------|-------------|--------------|
| 话题距离 | 两个topic的scope关键词重叠度 | 完全重叠 | 无重叠 |
| 目标冲突 | 两个topic的目标是否矛盾 | 目标一致或互补 | 目标直接矛盾 |
| 术语重载 | 相同术语在两个topic中是否有不同含义 | 无共享术语或含义一致 | 多个术语含义冲突 |
| 输出格式差异 | 两个topic期望的输出格式是否兼容 | 同类格式 | 完全不同格式 |
| 历史偏置强度 | 前一个topic的上下文残留是否会误导当前topic | 无残留风险 | 强残留（长对话、深度讨论） |

**阈值设计理由**：三档划分（low/medium/high）对应三种agent行为。阈值30和60是基于"大约三分之一切分"的初始值，将在evals测试和真实使用中校准。

| 分段 | 等级 | Agent行为 |
|------|------|----------|
| 0-30 | low | 静默继续 |
| 31-60 | medium | 回复开头简要提示上下文继承范围 |
| 61-100 | high | 主动建议话题处理策略，加载SKILL.md |

### 8. SKILL.md工作流（5步）

```
1. Detect Topic Event     → 识别话题变更信号
2. Classify & Score       → 确定关系类型 + 污染风险评分
3. Decide Context Policy  → 继承/隔离/确认策略
4. Build Context Package  → 生成当前任务专用上下文包
5. Update Topic Registry  → 更新本地topic状态 + 记录决策
```

### 9. AGENTS.md always-on规则

安装时合并到目标项目的指令文件。核心行为：

- 每次交互前：调用`topic_detect`，根据risk等级决定行为
- 每次交互后：如有实质性成果，调用`topic_update`更新topic状态
- 风险≥high时：自动加载context-router skill执行深度治理
- MCP不可用时：不报错，不阻塞，在回复中附带降级提示

## 设计决策记录

| 决策 | 选择 | 理由 |
|------|------|------|
| 触发方式 | AGENTS.md注入 + MCP | AGENTS.md在每次交互前被读取，可在其中写入"调用MCP检查topic状态"的指令。这不是真正的middleware拦截，而是通过指令引导agent主动调用MCP tools。优势：不依赖平台改造；劣势：agent可能忽略指令，需要通过evals验证遵从率。 |
| 存储格式 | JSON | Python stdlib原生支持`json`模块，零外部依赖。JSON对人类的可读性略低于YAML，但避免了引入PyYAML依赖或手写解析器。结构化数据用JSON，叙述性内容（Context Package）用Markdown。 |
| MCP transport | stdio | 本地使用的标准方式，与OpenCode MCP配置兼容。 |
| 污染评分 | 规则驱动（非ML） | 可解释（用户可理解每个维度的评分来源）、可调（用户可手动覆盖）、零依赖（不需要模型推理）。代价是对复杂语义关系的识别能力有限，但对于"两个topic是否应该隔离"这个判断，规则方法足够。 |
| 7种关系类型 | 全部保留 | 4种（continue/switch/fork/reset）可高可靠检测，3种（merge/archive/bridge）检测置信度较低。保留全部7种以覆盖完整场景，但对低置信度类型增加用户确认环节而非自动执行。 |
| Topic维护 | AI自动 + 用户确认 | 降低维护成本。高置信度操作（continue、switch）自动执行，低置信度操作（merge、bridge）提示确认。 |

## 约束与边界

- 第一版不做跨项目topic共享（每个项目独立`.ai-context/`）
- 第一版不做数据库后端（JSON文件足够）
- 第一版`topic_detect`基于规则和关键词，不依赖外部模型
- MCP server纯Python，零外部依赖，`requires-python >= 3.9`
- `.ai-context/`目录建议加入`.gitignore`（包含会话级临时数据）
- 并发写入通过文件级锁 + atomic write（写临时文件再rename）保护

## 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| MCP server未启动 | Layer 1降级为无感知 | AGENTS.md中增加fallback规则：MCP不可用时退化为手动模式，不报错 |
| topic_detect过度触发 | 用户体验差 | 严格阈值 + evals测试覆盖 + medium等级只提示不执行 |
| JSON文件冲突（多session并发写入） | 数据丢失 | 文件级锁 + atomic write（写temp再rename） |
| .ai-context/目录过大 | git仓库膨胀 | archive操作清理旧context package + 安装时自动添加.gitignore |
| Agent忽略AGENTS.md中的指令 | always-on层失效 | evals测试agent遵从率，指令措辞迭代优化 |
| merge/archive/bridge误检测 | 执行了错误的上下文操作 | 低置信度类型强制用户确认 |
