仔细阅读以下对话，并在充分理解需求并辩证看待分析以后，制定我们的开发计划。Ensure the style of this skill set is aligned with our existing skills'. Moreover, I think it is very important for us to decide when to load this skill set and how to auto-load this skill when necessary. 

---

可以，而且我认为**非常适合作为“说人话skill”的补充模块**。但它不应该被写成“永远禁止这些表达”，而应该写成一个**AI腔风险检测器**：发现这些模式后，要求模型判断是否真实有用；没有信息增量就删掉、改短、改实。

这里的关键是：skill不应只写抽象原则，而要写成可执行的检查规则。skills最佳实践也强调，skill应提供具体流程、gotchas、输出模板和验证循环，而不是泛泛地说“写得自然一点”。这组“AI slop四特征”正好可以放进gotchas或审稿清单。

## 我建议这样补充

### 1. 增加一个“AI腔负面清单”

可以放在`human-writing/SKILL.md`里：

```markdown
## AI腔风险检查

在完成初稿后，必须检查以下四类AI腔痕迹：

1. 破折号滥用
   - 典型问题：用“——”强行制造节奏、转折、总结感。
   - 处理方式：能用逗号、句号、冒号表达的，不用破折号。
   - 例外：中文论文标题副标题、解释性插入语、强烈转折可保留。

2. 英文AI高频词
   - 警惕delve, nuanced, robust, seamless, leverage, transformative等词。
   - 处理方式：改成具体动作、对象、约束或结论。
   - 例外：技术文档中这些词有明确技术含义时可保留。

3. 三人组排比
   - 典型问题：总是写成“A、B和C”“更快、更准、更安全”“效率、质量、体验”。
   - 处理方式：只保留真正需要并列的要素；能解释因果时，不堆名词。
   - 例外：正式定义、课程框架、章节结构、政策口径可保留。

4. 空洞not X but Y
   - 典型问题：“不是简单的工具，而是……”“不仅是……更是……”
   - 处理方式：如果后半句没有具体机制、对象、结果，就删掉。
   - 例外：用于纠正误解、重新定义概念、提出核心立场时可保留。
```

### 2. 增加一个“改写动作表”

这比单纯列禁忌更重要：

| AI腔模式         | 不好的写法                                    | 更好的处理                            |
| ------------- | ---------------------------------------- | -------------------------------- |
| 滥用破折号         | 这不是一个工具——而是一个平台                          | 这是一个平台，负责统一调度工具、上下文和执行状态         |
| 三人组排比         | 提升效率、质量和体验                               | 减少重复配置，并降低初始化出错率                 |
| 空洞not X but Y | 不是简单生成内容，而是重塑工作流                         | 它把需求澄清、目录初始化、规则生成和skill安装放到同一流程中 |
| 高级词堆叠         | nuanced approach to robust orchestration | 先判断任务类型，再加载对应skill，避免一次性塞入所有规则   |

### 3. 加入“保留条件”，避免过度清洗

这个很重要。否则skill会把正常的正式写作也改坏。

比如你的中文写作样本里，本来就有清晰的“三点式”结构。例如“信息安全产业高速度发展的原因有三：一是……二是……三是……”这种结构并不是AI slop，而是正式论述中的组织方式。你的技术/论文写作也经常需要“背景、问题、方案、效果”的分层论证，这种结构不应被误杀。

所以规则应写成：

```markdown
不要机械删除所有排比。只有当并列项空泛、互相重叠、无法展开为具体内容时，才视为AI腔。
```

### 4. 加入“说人话评分卡”

我建议补一个5分制：

```markdown
## 说人话评分卡

每段完成后按以下标准自评：

- 信息密度：是否提供了具体对象、动作、原因、结果？
- 句子自然度：是否像真实作者会写的话？
- 结构必要性：排比、转折、总结是否服务论证？
- 术语克制：术语是否必要，是否解释清楚？
- 风格一致性：是否符合用户已有写作风格？

低于4分的段落必须改写。
```

### 5. 放入eval，而不是只放进SKILL.md

尤其是这种风格类skill，最好做小型eval。技能评估文档建议用真实prompt、期望输出和断言来测试skill是否带来稳定改进。我们可以为“说人话skill”增加这类断言：

```json
{
  "assertions": [
    "输出没有无信息增量的not X but Y结构",
    "输出没有连续三处三项排比",
    "英文文本没有滥用delve、nuanced、robust等AI高频词",
    "中文文本中破折号使用不超过必要场景",
    "每个核心判断后至少包含一个具体解释、例子或边界条件"
  ]
}
```

## 我的结论

这四条非常有价值，但它们更适合作为：

**human-writing skill里的“AI slop检测与改写模块”**，

而不是独立成一个大skill。

它的定位应是：

> 识别AI生成文本中常见的“假深刻、假流畅、假结构化”痕迹，并把它们改成更具体、更直接、更符合真实作者习惯的表达。

我建议我们在V4版本里增加三个文件：

```text
human-writing/
├── SKILL.md
├── references/
│   ├── ai-slop-detector.md
│   ├── chinese-natural-writing.md
│   └── english-natural-writing.md
└── evals/
    └── evals.json
```

其中`ai-slop-detector.md`专门写这四类问题、触发条件、例外条件和改写示例。
